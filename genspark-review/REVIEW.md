## 1. ملخص المشروع (إيه اللي بيعمله)

منظومة تفريغ صوتي (Speech-to-Text) بالعربي/العامية المصرية مبنية على Gemini API، بتشتغل بثلاث واجهات في نفس الوقت:

| الواجهة | الملف | الوصف |
|---|---|---|
| 🤖 بوت تليجرام | `telegram_bot.py` | Long-polling، يستقبل فويس/ملف صوتي ويرد بالنص في code block. يكتشف مفاتيح API المرسلة في الشات ويضيفها تلقائياً |
| 🌐 واجهة ويب | `web_service.py` | خادم `http.server` خام (Pure Python) + صفحة HTML مدمجة فيها تسجيل MediaRecorder ورفع ملفات وإضافة مفاتيح |
| 💻 أداة سطح مكتب | `transcribe_tool.py` + ملفات `.bat` | تفرّغ آخر تسجيل في مجلد Windows وتنسخه للحافظة |

**الطبقات المشتركة:**
- `config.py` — الثوابت: قائمة الموديلات، الـ System Prompt، المسارات، الـ cooldown.
- `key_manager.py` — Singleton يدير `keys.json` (حالة المفاتيح، cooldown عند 429، إحصائيات).
- `transcriber.py` — المحرك: يلف على الموديلات الثلاثة × المفاتيح النشطة لحد ما ينجح.
- `main.py` — يشغّل الويب في Thread خلفي + البوت في الـ Thread الرئيسي.

**الاعتمادية الوحيدة:** `requests>=2.31.0` (وده شيء كويس جداً من ناحية البساطة).

**حجم الكود:** 1293 سطر Python عبر 7 ملفات (منهم ~480 سطر HTML/CSS/JS مدمجين في `web_service.py`).

## 4. المشاكل المكتشفة (مرتبة من الأخطر للأقل)

### 🔴 4.1 حرجة (أمان) — لازم تتصلح قبل أي نشر عام

#### P1. واجهة الويب مفتوحة بالكامل بدون أي مصادقة
- **المكان:** `web_service.py` — كل الـ endpoints (`/`, `/api/transcribe`, `/api/add_key`, `/api/status`)، والخادم بيسمع على `0.0.0.0`.
- **المشكلة:** أي حد يوصل للـ URL يقدر:
  - يستهلك كوتا مفاتيحك (65 طلب/يوم/مفتاح — تخلص في دقايق).
  - يضيف مفاتيح وهمية لـ `keys.json` ويفسد الـ Pool.
  - يقرأ `/api/status` اللي فيه أسماء المشاريع وأول 8 أحرف من كل مفتاح.
- **الخطورة:** عالية جداً عند النشر على استضافة (الـ README بيوجّه للنشر على Bot-Hosting/Cloud).
- **الحل المقترح:** توكن بسيط `WEB_ACCESS_TOKEN` من متغير بيئة، يُطلب في Header أو كـ `?token=` ويُحفظ في localStorage في الواجهة. لو المتغير فاضي → السماح على `127.0.0.1` فقط مع تحذير.

#### P2. `/api/add_key` يقبل أي نص كمفتاح بدون تحقق
- **المكان:** `web_service.py:555-561` و `key_manager.py:186`.
- **الدليل:** `POST /api/add_key {"key":"zzz"}` → `200 OK` واتضاف "zzz" كمفتاح نشط. (تم اختباره فعلياً)
- **الأثر:** مفتاح وهمي يدخل حلقة التدوير → كل طلب تفريغ يضيع وقت على 3 محاولات فاشلة (موديل × مفتاح وهمي) قبل ما يوصل للمفتاح الصح.
- **الحل:** استخدام `KeyManager.extract_key_from_text()` الموجود فعلاً للتحقق من الصيغة قبل `add_key()` (البوت بيعمل كده، الويب لأ).

#### P3. ملف `keys.json` بيتخزن فيه مفاتيح API وتوكن تليجرام كنص صريح
- **المكان:** `key_manager.py:44-49`.
- **المشكلة:** الملف بيتكتب بصلاحيات افتراضية (عادة `644` = قابل للقراءة لأي مستخدم على السيرفر). على استضافة مشتركة ده خطر.
- **الحل:** `os.chmod(path, 0o600)` بعد الكتابة + كتابة ذرّية (temp → rename) لتجنب تلف الملف لو العملية اتقفلت أثناء الحفظ.

#### P4. مفتاح الـ API في الـ URL (Query String)
- **المكان:** `transcriber.py:55` — `?key={key_str}`.
- **المشكلة:** الـ URL ممكن يتسجل في logs/proxies. Google توصي رسمياً بـ Header `x-goog-api-key`.
- **الحل:** نقل المفتاح لـ Header. تغيير سطرين.

#### P5. Chat ID شخصي ثابت في الكود وفي `.env.example` و `README`
- **المكان:** `config.py:50` (`DEFAULT_CHAT_ID = "1124247595"`)، `.env.example:14`، `README.md:66`.
- **المشكلة:** ده Chat ID حقيقي لصاحب المشروع. مش "سر" خطير لكنه معلومة شخصية في repo عام، وأي حد ينسخ المشروع من غير ما يغيّره هيبقى بوته مفتوح لصاحب الـ ID ده. كمان الـ README فيه توكن جزئي (`8158611188:AAGbrz...`) ويوزرنيم البوت الحقيقي.
- **الحل:** `DEFAULT_CHAT_ID = ""` (فاضي = البوت يرفض الكل لحد ما يتضبط) + تنظيف الأمثلة لقيم وهمية واضحة.

### 🟠 4.2 مهمة (Bugs وظيفية) — بتأثر على الدقة والاستقرار

#### P6. Parser الـ multipart بيقطع بيانات الصوت الحقيقية
- **المكان:** `web_service.py:535` — `.rstrip(b"\r\n")`.
- **الدليل (اختبار فعلي):** حمولة 12 بايت تنتهي بـ `\r\n\r\n` → وصلت للمحرك 8 بايت. **DATA CORRUPTED.**
- **الأثر:** أي ملف صوتي بياناته الفعلية بتنتهي بـ `0x0D`/`0x0A` (احتمال ~1/128 لكل بايت أخير، وأكتر في بعض الصيغ) هيوصل ناقص → تفريغ غلط أو رفض من Gemini.
- **الحل:** قطع آخر `\r\n` واحد بالضبط (`part[header_end+4:-2]`) أو استخدام `email.parser`/`multipart` الصحيح.

#### P7. Parser الـ multipart يفشل مع boundary مقتبس
- **المكان:** `web_service.py:526`.
- **الدليل (اختبار فعلي):** `Content-Type: multipart/form-data; boundary="----XYZ"` → وصل 25 بايت بدل 12 (الـ body كله بما فيه الـ headers).
- **الأثر:** بعض المتصفحات/العملاء بيبعتوا الـ boundary بين علامات اقتباس (مسموح في RFC 2046). الحمولة تبقى مشوّهة.
- **الحل:** `boundary.strip('"')` + التعامل مع `;` بعده.

#### P8. `do_POST` لمسار غير معروف بيقفل الاتصال بدون رد
- **المكان:** `web_service.py:514-570` — مفيش `else`.
- **الدليل:** `POST /api/unknown` → `RemoteDisconnected`.
- **الحل:** إضافة `else: 404`.

#### P9. طلبات تليجرام بدون `timeout` → البوت ممكن يتجمّد للأبد
- **المكان:** `telegram_bot.py:88, 96, 102` (sendChatAction, getFile, تحميل الملف).
- **المشكلة:** `requests` بدون timeout بيستنى إلى ما لا نهاية لو الشبكة علّقت. والـ `except` الخارجي مش هيمسكه لأنه مش exception.
- **الحل:** إضافة `timeout=` لكل الطلبات.

#### P10. البوت متسلسل (Sequential) — فويس طويل بيوقف كل الرسائل التانية
- **المكان:** `telegram_bot.py:64` — حلقة واحدة تعالج التحديثات واحد واحد.
- **المشكلة:** لو التفريغ أخد 40 ثانية، أي رسالة تانية (حتى `/status`) تستنى.
- **الحل:** `ThreadPoolExecutor` صغير (2-3 workers) للتفريغ، أو على الأقل معالجة الأوامر النصية قبل الصوت.

#### P11. خادم الويب أحادي الـ Thread
- **المكان:** `web_service.py:578` — `HTTPServer` بدل `ThreadingHTTPServer`.
- **المشكلة:** طلب تفريغ واحد (60 ثانية timeout) يوقف الصفحة وكل الطلبات التانية.
- **الحل:** تغيير كلمة واحدة: `ThreadingHTTPServer` (موجود في الـ stdlib من Python 3.7).

#### P12. استثناءات مبتلعة بصمت (Silent Exceptions)
- **المكان:** `telegram_bot.py:153-154` — `except Exception as e: time.sleep(3)` بدون أي طباعة.
- **المشكلة:** لو حصل خطأ في معالجة رسالة (مثلاً `KeyError` في بنية الـ update)، البوت يسكت ويعيد المحاولة، والمطور ما يعرفش فيه إيه. وكمان `offset` ممكن ما يتحدثش → نفس الرسالة تتعالج تاني في loop.
- **الحل:** `logging` بدل `print` + طباعة الاستثناء + ضمان تحديث الـ offset.

#### P13. Race Condition على `keys.json` بين الـ Threads
- **المكان:** `key_manager.py` — `save()` تُستدعى من Thread الويب و Thread البوت بدون قفل.
- **المشكلة:** كتابتين متزامنتين ممكن تنتج JSON تالف → عند إعادة التشغيل `load()` تفشل → `_bootstrap_from_legacy()` تمسح كل المفاتيح المضافة من الشات!
- **الحل:** `threading.Lock` حول `save()` وعمليات التعديل + كتابة ذرّية.

#### P14. `get_active_keys()` ترجع كل المفاتيح (حتى المستهلكة) لو كلها في cooldown
- **المكان:** `key_manager.py:135-137`.
- **المشكلة:** النية كويسة ("حل أخير") لكن النتيجة: كل مفتاح مستهلك هيتضرب تاني بـ 429 ويتجدد الـ cooldown له ساعة كاملة من جديد → **المفاتيح عمرها ما هتتفك** طالما فيه استخدام مستمر.
- **الحل:** إما ترجع قائمة فاضية مع رسالة واضحة "كل المفاتيح في تهدئة، أقرب مفتاح يرجع بعد X دقيقة"، أو ما تجددش الـ cooldown لو المفتاح أصلاً مستهلك.

#### P15. ترتيب الحلقات يضيّع كوتا 3.8 Flash على المفاتيح
- **المكان:** `transcriber.py:50-52` — `for model: for key:`.
- **المشكلة:** لو المفتاح 1 أخد 429 على 3.8 Flash، الكود يعلّمه "exhausted" **بالكامل** (كل الموديلات) مع إن كوتا 3.6 و 3.5 Transcribe على نفس المفتاح لسه سليمة (كل موديل له كوتا مستقلة حسب التقرير بتاعك نفسه). ده يضيّع 45 طلب من كل 65!
- **الحل:** تتبع الـ exhaustion على مستوى `(key, model)` مش `key` بس. ده تغيير متوسط في `key_manager.py`.

### 🟡 4.3 تحسينات (جودة وأداء وتجربة مستخدم)

#### P16. مفيش اختبارات نهائياً
- لا `tests/`, لا `pytest`, لا CI. كل الـ bugs فوق كانت هتتمسك بـ 5-6 اختبارات بسيطة.
- **الحل:** مجلد `tests/` مع pytest لـ: `extract_key_from_text`, `add_key` validation, multipart parser, cooldown logic, web endpoints (مع mock للـ Gemini).

#### P17. `print` بدل `logging`
- كل الملفات بتستخدم `print`. على استضافة 24/7 مفيش timestamps ولا مستويات ولا إمكانية إخفاء الـ debug.
- **الحل:** `logging.basicConfig` في `main.py` + استبدال تدريجي.

#### P18. الـ cooldown ساعة ثابتة بينما الكوتا يومية
- **المكان:** `config.py:47`.
- **المشكلة:** الـ 429 من كوتا يومية (RPD) معناه المفتاح مش هيرجع إلا نص الليل بتوقيت Pacific. بعد ساعة هيتضرب تاني ببلاش. (ملاحظة: Google بترجع `retryDelay` في body الـ 429 — ممكن نستخدمه).
- **الحل:** قراءة `retryDelay`/`Retry-After` من الرد لو موجود، وإلا cooldown أطول أو حتى منتصف الليل PT.

#### P19. مفيش حد لحجم الملف المرفوع
- **المكان:** `web_service.py:517` — `rfile.read(content_length)` بأي حجم.
- **المشكلة:** ملف 500MB → استهلاك ذاكرة كامل + base64 يضاعفه 1.33x. Gemini inline_data حدها ~20MB أصلاً.
- **الحل:** رفض `Content-Length > 25MB` بـ 413 ورسالة واضحة.

#### P20. HTML/CSS/JS (480 سطر) مدمجين في ملف Python
- **المكان:** `web_service.py:18-495`.
- **المشكلة:** صعب التعديل، مفيش syntax highlighting، أي تغيير في الـ UI يعدّل ملف الـ backend.
- **الحل:** نقل لـ `static/index.html` وقراءته عند الطلب (أو عند بدء التشغيل). **تغيير آمن ومحدود.**
- ⚠️ **قرار مطلوب منك:** هل تفضّل الملف الواحد للنشر السهل، ولا الفصل؟

#### P22. الـ `mime_type` من تليجرام لـ `document`

- **قرار مطلوب منك:** هل تحب نحتفظ بالأسماء العربية (لسهولة الاستخدام على ديسكتوب Windows) ولا نضيف نسخ بأسماء إنجليزية؟ **أنا أميل للاحتفاظ بيها** لأن ده هدفها.

#### P27. `extract_key_from_text` مع مفاتيح أطول من المتوقع
- الـ regex `AIzaSy[a-zA-Z0-9_-]{33}` بيمسك **أول 33 حرف بالضبط** حتى لو النص أطول → لو Google غيّرت الطول، المفتاح هيتقطع بصمت.
- ملاحظة بسيطة (مفاتيح Google الحالية 39 حرف فعلاً)، لكن يستحق `\b` في آخر الـ pattern.
