## 2. الصمامات الثلاثة [إجماع ج15 + رأينا]

### 2.1 الصمام الأول — Heartbeat Watchdog (مراقبة النبض لا الحياة)

**المشكلة:** `main.py` l.135 يسأل "هل الخيط حي؟" — والجواب نعم دائماً حتى وهو عالق.
**الحل:** يسأل "متى آخر مرة **نجح** فيها `getUpdates`؟" — والقيمة **موجودة بالفعل**: `STATE["last_poll_ok"]` (`telegram_bot.py` l.422).

```
كل WATCHDOG_INTERVAL (30ث):
  idle = now - STATE["last_poll_ok"]
  if idle > HEARTBEAT_STALL_SECONDS (90):      # ≥ 2× مهلة polling الكاملة
      سجّل "stall detected" + أرسل إشعاراً (لو يمكن الإرسال)
      اطلب من حلقة البوت: stop_event.set()
      انتظر حتى 10ث ثم ابدأ خيط بوت جديد بـ Session جديدة
      bot_restarts += 1
  if bot_restarts في آخر 10 دقائق > 3:
      ادخل "وضع الحماية": مهلة أطول (sleep 60) + إشعار "الشبكة غير مستقرة"
```

**تفاصيل مهمة [رأينا]:**
- يجب أن تحترم حلقة البوت `stop_event` **داخل** الانتظار؛ `requests.get` العالق لن يرى الحدث → لذلك إعادة إنشاء الخيط ضرورية (ترك القديم يموت وحده) — نفس ما يحدث الآن عند `is_alive()==False` لكن بمحفّز صحيح.
- **`last_poll_ok` يُحدَّث فقط عند 200 OK** (كما هو الآن) — لا تحدّثه عند الاستثناءات وإلا يعمى الـ watchdog ثانية.
- النبض يجب أن يشمل أيضاً **"آخر معالجة فويس نجحت"** (`last_job_ok`) لرصد التعليق داخل الـ worker لا الـ poller فقط.
- ضع **ساعة النبض ذاتها في `/status`** و`/health` (الويب): "آخر poll ناجح منذ Xث".

### 2.2 الصمام الثاني — فرق المهلات (Timeout Differential)

**القاعدة:** `client_read_timeout ≥ polling_timeout + 15` و**افصل connect عن read**.

| البارام | الآن | المقترح | ملاحظة |
|---|---|---|---|
| `getUpdates` `timeout=` (long poll) | 30 (مكتوب حرفياً l.407) | `Config.TG_POLL_TIMEOUT = 30` | يبقى 30 |
| `requests` timeout | `40` (رقم واحد لـ connect+read) l.413 | `(Config.TG_CONNECT_TIMEOUT=10, Config.TG_POLL_TIMEOUT + 15 = 45)` | tuple |
| `getFile` | `TELEGRAM_TIMEOUT=30` | `(10, 30)` | كافٍ — استجابة صغيرة |
| تحميل الملف | `TELEGRAM_DOWNLOAD_TIMEOUT=60` | `(10, max(60, 20 + 15×MB))` | ديناميكي كما في Gemini |
| `sendMessage` | 30 | `(10, 30)` | |

> ملاحظة دقة: الحادث 03 كان بمهلة 30ث على التحميل؛ الكود الحالي **بالفعل** 60ث (`TELEGRAM_DOWNLOAD_TIMEOUT`). لكن 60 ثابتاً مع 4 تحميلات متزامنة قد لا يكفي — الحل الحقيقي هو **FIFO** لا رفع المهلة.

### 2.3 الصمام الثالث — طابور FIFO صارم

**القرار [قرار-مالك]:** الطابور يعمل **دائماً**، مع جلسة أو بدونها؛ الترتيب مُلزم؛ إيصال فوري.

**التصميم [رأينا — يعدّل اقتراح ج10]:**
- [ج10] اقترح `asyncio.Queue`. **مرفوض**: الكود كله خيوط + `requests` المتزامنة؛ إدخال asyncio يعني إعادة كتابة البوت كله ويخالف "اعتماد واحد". نستخدم `queue.Queue` القياسي + **worker واحد** للتحميل+التفريغ (FIFO حقيقي) + **worker ثانٍ للإرسال فقط** (لا يُعطَّل التفريغ بسبب بطء تليجرام في الإرسال).
- `BOT_WORKERS=2` الحالي يُعاد تعريفه: `TRANSCRIBE_WORKERS=1` (قابل للرفع إلى 2 بموافقة — لكن يكسر FIFO الصارم) + `SEND_WORKERS=1`.
- **إيصال فوري** عند الاستلام: `⏳ تم الاستلام — رقمك في الطابور: 2/5` (رد على الفويس). يُعدَّل لاحقاً إلى "🎙️ جارٍ التفريغ…" ثم يُحذف عند الإرسال (`editMessageText`/`deleteMessage` موجودان).
- **تحميل الملف داخل الـ worker لا في الـ poller** (كما الآن) لكن **متسلسلاً** → لا تصادم.
- تحميل بـ **retry ×3** (backoff 2/5/10) ومهلة ديناميكية؛ فشل التحميل ≠ فشل التفريغ → رسالة مميزة "تعذر تحميل الفويس من تليجرام" (يعالج G15).
- حد أقصى للطابور (`QUEUE_MAX=50`): عند الامتلاء يُرفض الفويس برسالة واضحة بدل انهيار صامت (backpressure).

### 2.4 `requests.Session` واحد لكل خيط + إعادة إنشاء

- Session للـ poller، Session للـ worker، Session للمرسل (الـ Session ليس thread-safe للتعديل لكن الاستخدام المتوازي للقراءة مقبول عملياً؛ الأسلم واحد لكل خيط).
- عند `ReadTimeout`/`ConnectionError` في الـ poller: `session.close()` وأنشئ واحدة جديدة قبل المحاولة التالية (علاج ghost socket).
- `HTTPAdapter(pool_connections=4, pool_maxsize=8, max_retries=0)` — إعادة المحاولة بأيدينا لا بأيدي urllib3 (حتى نسجّل ونصنّف).

## 3. استمرارية المهام (Job Persistence) — هل هي P0؟

[ج1] M03 و[ج3] "journal + outbox" يقترحان حفظ كل مهمة على القرص.
**[رأينا]:** نقسمها:

| الجزء | الأولوية | السبب |
|---|---|---|
| **سجل مهام ndjson بسيط** (`jobs.ndjson`: received/downloaded/transcribed/sent/failed مع `update_id`, `file_id`, `message_id`) | **P0** | رخيص جداً (سطر لكل حالة)، يجعل `/trace` و`/replay` ممكنين، ويكشف أين مات الفويس |
| **إعادة تشغيل المهام غير المكتملة بعد restart** | **P1** | يحتاج `file_id` فقط (تليجرام يحتفظ بالملف ساعات) — لا نحفظ الصوت؛ تليجرام هو التخزين |
| **Outbox** (حفظ النص قبل الإرسال؛ إن فشل الإرسال لا نعيد التفريغ) | **P0** مع الأرشفة | النص يُكتب في الأرشيف **قبل** `sendMessage` → مجاناً يصبح لدينا outbox |
| حفظ ملف الصوت نفسه | **مرفوض افتراضياً** (`KEEP_AUDIO=0`) | مساحة + خصوصية؛ يحتاج موافقة صريحة |

**مفاتيح الـ idempotency:** `update_id` (تليجرام) + `file_unique_id` (ثابت للملف) — إن ظهر نفس `file_unique_id` خلال 24ساعة → لا نعيد التفريغ، نرسل النتيجة المحفوظة.
